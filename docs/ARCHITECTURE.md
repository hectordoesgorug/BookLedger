# BookLedger Architecture (initial)

## Modules
- `bookledger.app`: main window, navigation, and page composition.
- `bookledger.ui.forms`: intake/edit form and field-level feedback.
- `bookledger.db.database`: SQLite connection setup, versioned schema migration, canonical locations, integrity checks, consistent snapshots.
- `bookledger.services.catalog`: validation, duplicate lookup, copy creation/editing, canonical location management, contextual price and explicit status/sales rules.
- `bookledger.services.isbn`: ISBN normalization, check-digit validation, and safe ISBN-10/ISBN-13 alias conversion (978 ISBN-13 only).
- `bookledger.services.metadata`: provider orchestration, field merging, and lookup outcomes. Open Library is primary, Google Books is the fallback/enrichment provider, and Booktopia is the final HTML enrichment source for supported missing fields.
- `bookledger.services.booktopia`: bounded HTTPS ISBN-search and product-page adapter. It verifies page ISBN evidence, parses matched schema.org Book data and standard description markup, and does not use Booktopia prices.
- `bookledger.services.photos`: image orientation, resizing, and JPEG compression.
- `bookledger.services.lifecycle`: durable trash, restore, clear, purge, and explicit recovery of file/database operations.
- `bookledger.services.verification`: read-only relational and managed-photo-tree consistency checks.
- `bookledger.services.backups`: verified backup archives and restore workflow.
- `bookledger.paths`: portable data locations and verified legacy-file migration.

## Data ownership
`book_records` owns bibliographic metadata shared by an edition/ISBN, including the main Title and optional Subtitle. `copies` owns physical-copy fields, the one current Price, and stable Copy IDs. `sales` is an append-only history of Price/date events; status reversals keep their recorded history and do not void revenue. A later transition back to Sold appends another event. Photo paths are stored relative to the portable data folder so moving the folder does not invalidate image references.

## Copy identity
Each copy receives an immutable UUID stored in `copies.copy_uuid`; this is its permanent identity across edits, status changes, backups, and restores. The existing integer `copies.id` remains a local row handle for current SQLite foreign keys and GUI callbacks. `copy_code` remains the human-facing `BL-` identifier, formatted from that local ID and displayed in reports and messages. UUIDs are not derived from either value. Schema v7 adds the UUID to existing copies without changing their row IDs or visible codes. Schema v8 adds reusable poster template definitions without changing book or copy records. The app does not yet merge independent libraries; UUIDs alone do not identify duplicate physical books.

## UI/business boundary
Metadata providers' full returned titles remain in Title; the app never splits them automatically, and users may move subtitle text into Subtitle themselves.

UI callbacks gather input and display service results. Core validation and persistence rules are enforced in `CatalogService` and SQLite constraints. Long-running metadata lookup runs off the UI event thread, with provider activity, provider outcomes, and the overall result passed back through a UI queue and applied on Tk's thread. Each provider outcome distinguishes a confirmed miss, an unverified returned record, a matched record with sparse metadata, a recognized unavailable product, and categorized lookup failures; user-visible diagnostics avoid raw exception details. Partial results without a description are reported as such, including when Book Details is unavailable. Operation IDs and the requested ISBN guard against stale callbacks after an ISBN change, form clear, or newer lookup. The application configures Open Library, Google Books, Archive.org, then Booktopia. Open Library queries the exact ISBN and its valid ISBN-10/13 alias together, but does not provide Book Details/Synopsis from edition descriptions, notes, excerpts, or linked-work descriptions. Google Books tries the exact raw ISBN, the exact `isbn:` query, then the equivalent `isbn:` query when needed; it scans all returned volumes and combines non-empty fields only from candidates whose ISBN matches either valid representation. Sparse matching results do not prevent later candidates or query variants from supplying a description. Google identifiers must match either valid representation, while Open Library accepts a response keyed to the requested ISBN if identifiers are absent and rejects conflicting identifiers. Booktopia queries `search.ep?keywords={isbn}`, follows at most two HTTPS links on Booktopia whose product URL carries the requested ISBN or valid alias, and requires a matching ISBN on the product page. If the search request returns an HTTP error without a verified product, it makes one request to `https://booktopia.com.au/book/{isbn}.html/`; the normal redirect handler permits only same-site HTTPS redirects. Data from that fallback is accepted only when the final URL is a slugged canonical product URL and the page independently verifies the requested ISBN. It reads title, author, publisher, publication year, edition, page count, and recognized print format from the matching schema.org Book object. For Book Details, it uses the Description panel only when the `#pdp-tab-description` tab explicitly identifies that panel through `aria-controls`, an in-page `href`/target relationship, or the panel's `aria-labelledby`. If there is no linked panel, a matching schema.org Book description is considered after rejecting recognized bibliographic-note and retail boilerplate text. Generic page metadata and unassociated `itemprop="description"` content are not used. If no usable synopsis remains, Book Details stays empty. An explicit page message that the book cannot be sourced, or a matching structured `OutOfStock`, `Discontinued`, or `SoldOut` value, sets the provider outcome to `Product unavailable` without treating the matched ISBN as missing. A Booktopia HTTP error body may still be used if its final URL is the canonical URL for the requested ISBN, page ISBN evidence matches, and supported metadata is present; otherwise the original HTTP/provider failure is retained. Booktopia does not map product price to Price or SRP. Booktopia pages with no ISBN evidence are reported as unverified; unexpected parsing errors remain provider failures rather than ISBN misses. Google Books `volumeInfo.description` is supported. Provider-derived titles are normalized, and values are merged into empty controls only, preserving both earlier provider values and user input. The Add Book form includes a photo preview and simulated BookLedger Mobile connection and ISBN scanning controls. Metadata providers can be replaced without changing the catalog schema or form workflow.

Booktopia uses standard-library HTML parsing only; there is no browser automation or additional dependency. It caps each response at 2 MiB, applies the provider's ten-second timeout to each request, and restricts redirects/product links to HTTPS Booktopia hosts. The same size and host checks apply to HTTP error bodies. A search response may lead to at most two ISBN-10/ISBN-13 candidate requests; when the search request returns an HTTP error, one direct ISBN URL is attempted instead. A search response without a verifiable product link is reported as ISBN unconfirmed, not a confirmed miss. Provider skipping checks each provider's supported fields, including Book Details/Synopsis for Google Books and Booktopia; only missing values are merged. The form supports print format but has no language or series field; those attributes are not stored. Booktopia's current Terms of Business state that bibliographic data is copyrighted by Nielsen Book Services, publishers, or their licensors, but do not establish an automated metadata API or permission. This HTML integration is best-effort and subject to Booktopia's policies and page changes. Current live raw HTML and the Description-tab relationship were not available for inspection; synthetic fixture tests verify the relationship-aware parser but do not establish current live-site behavior.

Catalog and Inventory share `CatalogService.list_copies()` and the same active physical-copy rows; trashed and pending storage-operation rows are filtered centrally. Catalog presents one photo card per copy, including stable Copy ID, Price, and a gray overlay/red SOLD marker; double-click opens read-only More Details. Inventory presents a sortable detailed table; double-click edits the clicked row. Both expose the same right-click context menu; Delete moves exactly one copy to Trash. Dashboard counts and ordinary sales/revenue exclude copies in Trash. Restore preserves the row and its sales events; Clear Trash permanently removes those sales events and conditionally removes an unreferenced bibliographic record.

Schema v4 includes `trash_entries` and `storage_operations`. Trash metadata references the original copy row and records its previous status and deletion order. Storage operations make interrupted photo install/replace/trash/restore/cleanup detectable and expose explicit retry. Database transactions and file moves are coordinated by services; a filesystem operation is not considered complete while its durable journal remains.

Catalog renders `Title: Subtitle` only when the combined string is shorter than 60 characters; otherwise it renders the main Title. Catalog search matches Subtitle, while Catalog sorting remains based on main Title. Inventory always renders the combined string when Subtitle is present. Book Details shows the fields separately, and the poster `Title` field continues to use main Title only.

No-ISBN duplicate detection continues to compare exact main Title and Author. A legacy record that stored subtitle text inside Title may not match a newly separated Title and Subtitle automatically.

## Portable storage and migration
Schema v12 adds nullable `book_records.subtitle`; the v11 migration leaves existing Title values and all copy and sales data unchanged. Schema v13 adds the single library currency, validated exchange-rate cache, and append-only conversion audit; migration from v12 defaults the currency to PHP without changing any stored amount.

`AppPaths` resolves the project root during source development and the executable directory when frozen. Mutable application data is under `data/`: `bookledger.sqlite3`, `photos/{copy_id}.jpg`, `trash/{copy_id}.jpg`, `assets/` (custom logos and poster backgrounds), `posters/`, and `logs/bookledger.log`. Root-level `config.json` remains the canonical settings file and root-level `backups/` remains user-managed. Startup detects legacy `BookLedger_Data/` before database initialization, snapshots SQLite through its backup API, copies photos/assets/backups, checks the copied database, canonicalizes referenced old photos to per-ID JPEGs, and only then renames the legacy folder to a `.migrated` recovery folder. Both-database conflicts stop startup. Configuration updates use an atomic replacement and preserve unrelated JSON keys. If the root configuration cannot be read or written, the existing profile configuration may be used as a safe fallback; malformed source files are preserved.

New and replacement images are processed through `PhotoService` into `photos/.staging/` and become canonical only once fully decoded and compressed. New copies reserve their generated ID in SQLite and journal the canonical installation; replacements use same-volume atomic replacement so the old image remains until the staged replacement is ready. Mobile photo handoff and Choose Photo both call the same staging service.

## Trash and verification
Delete journals then moves one canonical photo to `trash/{copy_id}.jpg` and inserts a `trash_entries` row without deleting the copy or its sales history. Restore selects the latest Trash entry (LIFO), moves the original photo back, and removes Trash metadata only after the file move. Clear Trash deletes selected sales/copy/trash rows in a transaction, removes bibliographic records only when no copies remain, then removes unshared files; a cleanup failure remains in `storage_operations` for explicit retry. Purge requires two UI confirmations including the exact word `PURGE`, closes the diagnostic log before deleting the portable data tree, removes BookLedger's canonical and active fallback configuration files, then recreates a fresh default configuration and empty library. It retains root backups, preserves bundled resources and unrelated user files, and resets preferences and credentials. Diagnostic logging remains off after Purge, so the log is recreated only if logging is enabled again.

## Poster templates and rendering
Poster templates are stored in SQLite `poster_templates` with sequential preset labels, a relative background reference, and serialized field geometry. Coordinates and dimensions are normalized against the background canvas, so resizing the Tk preview does not alter the saved layout. New backgrounds use `template_background_N` filenames beneath `data/assets/`; templates reference them relatively as `assets/name`. Older references in root `assets/` or `data/poster_backgrounds/` remain readable and are promoted to `data/assets/` during backup restore. Generated posters are PNG files named from the physical copy ID under `data/posters/`. Backups include template definitions, managed data assets, and generated `BL-*.png` posters. Restore replaces generated posters while preserving unrelated files in `data/posters/`. Poster text uses Arial when available from the runtime and a system font fallback otherwise.

`VerificationService` does not mutate data. It checks SQLite integrity and foreign keys, copy identities, Trash consistency, unresolved storage operations, canonical and safe photo paths, missing active/trashed photos, unreferenced files, shared paths, and staging residue. Warnings do not trigger cleanup.

`config.json` is the canonical configuration document. It retains the existing `metadata_providers` section and holds `api_keys.google_books`, `preferences.genres`, `preferences.formats`, `preferences.locations`, `preferences.theme`, `preferences.currency`, `preferences.shop_url`, and the relative `preferences.shop_logo_path`; `logging.enabled` and `migration_state` record diagnostic logging and one-time legacy migration checks. SQLite `currency_state` is authoritative after currency operations; startup reconciles the JSON mirror and any interrupted-operation marker from that state. Database-wide conversion creates a verified recovery backup first, updates all retained copy prices, sales (including voided sales), and SRPs in one transaction, and writes rate provenance and affected-record counts to `currency_conversions`. Frankfurter rates are fetched only for explicit user-approved conversions, cached in SQLite with observation and retrieval dates, and rejected when more than five days old. Automated SRP is not integrated because no verified physical-edition source was established. All currency presentation uses ISO code, symbol, and two decimals; ordinary startup and browsing make no exchange-rate requests. The initial supported currencies are PHP, USD, EUR, GBP, JPY, AUD, CAD, SGD, CNY, HKD, KRW, INR, TWD, THB, MYR, IDR, NZD, CHF, AED, and SAR. Theme persistence stores internal theme names. New configurations prefer Clam when the native Tk theme is available, then Flatly, then the active or first available theme; saved theme selections are preserved. The `clam` option is applied through native Tk/Ttk, while Flatly, Light, and Dark use ttkbootstrap's registered theme API; unavailable saved names are ignored without deleting the stored value. If a saved Clam theme is unavailable in the platform's native Ttk installation, the status bar explains the fallback. A failed startup theme change is reported in the status bar. A selected shop logo is normalized to PNG under `data/assets/`, with its config reference relative to portable `data/`; it is included in asset backups and old managed custom logos are removed after a replacement or clear commits. The bundled default shop logo and interface resources resolve relative to the source or frozen resource root, never the process working directory. The Google Books key is stored as plain text and is never written to the activity log. Diagnostic logging is optional; activity records use event names and safe numeric IDs, rotate at 1 MB, and retain up to five rotated files. Backups include the canonical configuration and are not encrypted, so they may contain API credentials. A canonical key takes precedence over any older key; when absent, the portable `data/assets/google_books.json` value takes precedence over a profile legacy file. The portable legacy file is removed only after the root configuration has been written and read back successfully with the migration marker and when it contains no unrelated settings. Conflicting, malformed, or extra-field legacy files are preserved and are not active sources after the migration is checked. A profile legacy file is retained as recovery data but is inactive after the marker is written. Removing the canonical key does not re-import either legacy value.

Genre, Format, and Location options migrate once from SQLite configuration (`app_meta` and `locations`). Assigned historical values absent from those lists are retained as compatibility options. After migration, these option lists are read and written through `config.json`; SQLite continues to own book and copy assignments, sales, and all other operational records. Their displayed order is persisted in the same configuration lists without changing existing book assignments. Legacy `app_meta` and `locations` entries remain in the database as inactive migration data and are not synchronized with the canonical lists. `logging.enabled` migrates from `app_meta.diagnostic_logging_enabled`; the legacy value is no longer updated after migration.

Scrollable Tk sections register with one application-level mouse-wheel router. The router targets the nearest live section under the pointer, supports Windows wheel and high-resolution deltas plus X11 wheel buttons, preserves native text-entry, dropdown, list, and tree behavior, and unregisters sections when their views are destroyed. The form, About guide, Catalog cards, Preferences lists, genre chart, poster field palette, and copy-detail text viewer use their normal scroll widgets.

## Metadata provider registry and Archive.org

The default provider order is Open Library, Google Books, Archive.org, Booktopia, Bigbook, then Hardcover. The original four sources remain enabled by default; Bigbook and Hardcover are appended disabled until individually verified. Older provider settings retain their saved relative order and enablement for known providers, and newly registered providers are appended using their safe defaults. The registry supplies both the priority controls and the embedded ISBN Lookup Test provider choices.

Archive.org uses its public Advanced Search endpoint without an API key, requests up to ten records, and asks only for identifier, title, creator, publisher, year, edition, and description. It rejects titleless and obvious administrative records, collapses duplicate rows for the same Archive.org identifier while keeping distinct identifiers separate, and ranks candidates by bibliographic completeness. When multiple distinct candidates remain, it checks at most the three strongest records through their individual metadata endpoints and accepts a candidate only when its item metadata contains the requested ISBN or its valid ISBN-10/13 equivalent. It does not request ISBN fields in the initial search, fetch full item metadata for every hit, or combine fields across candidates. If ambiguous results cannot be verified, it returns an unverified no-data result. The provider interface exposes only the requested ISBN, so Archive.org cannot compare candidates against title or author already accepted from earlier providers; its selection is self-contained. It maps title, the first listed creator, publisher, year, edition, and sufficiently descriptive synopsis text. The item identifier is retained in the result source for diagnostics. Search and item verification share the adapter's five-second deadline.

Bigbook uses its documented ISBN search endpoint with the normalized ISBN-13 and sends the API key in the `x-api-key` header. It fetches returned item details only as needed and accepts metadata only when an ISBN-10 or ISBN-13 identifier verifies the requested ISBN (including a valid ISBN-10/13 equivalent). It maps title, authors, verified ISBN, publication year, page count, and description. Publisher and edition are unsupported because the documented response does not establish those fields. A second request may be needed for item details; search and detail retrieval share the adapter's five-second deadline. HTTP 402 is classified as exhausted daily quota and HTTP 429 as rate limiting. The adapter does not expose the API key in its request URL or error messages.

Hardcover uses its documented GraphQL endpoint and queries edition rows by both ISBN-13 and ISBN-10. The adapter verifies each returned edition's ISBN before mapping data. It maps book title, author names, ISBN, publisher, release year/date, edition information/format, page count, and edition or book description. Exact edition fields are used for publisher, format, ISBN, and page count; book-level fields are fallback sources for shared work metadata. The query uses documented `editions` and `books` fields and stays within Hardcover's documented query-depth limit. The personal token is sent in the `authorization` header. The provider API is in beta and is isolated in its own adapter. Both API credentials are stored as plain text in local `config.json`, as explicitly requested; backups include that configuration and are not encrypted, so credential-bearing backups must be protected accordingly.

## Snapshot backup and restore
Backups are versioned ZIP snapshots with a manifest of file sizes and SHA-256 checksums. They contain a consistent SQLite snapshot, managed `data/photos/`, `data/trash/`, `data/assets/`, generated poster PNGs, and root `config.json`. The activity log, caches, application binaries, and unrelated files outside those managed components are excluded. Backup names include a local timestamp and random suffix; an archive is published only after it validates. If a backup destination is inside managed data, that destination subtree is excluded from the snapshot. Older archives with backgrounds in root `assets/` or `data/poster_backgrounds/` remain restorable.

Restore replaces the current database, photos, trash, assets, and root configuration with the selected snapshot; it never merges later edits. The UI warns about the replacement and asks for confirmation. Before activation, BookLedger creates and retains a separate validated snapshot of the current library in `backups/`. The selected archive is checked for safe paths, supported manifest, checksums, valid configuration, SQLite integrity, foreign-key integrity, and referenced photos. Components are staged and activated under a durable recovery journal. If activation fails or the process stops mid-swap, the next startup restores the prior component set before opening the library. Successful restore keeps the pre-restore recovery archive. Restart BookLedger after restore so in-memory provider/configuration settings reload. Archives are not encrypted and may contain API credentials from `config.json`; store them accordingly. Restore does not promise to retain excluded logs, caches, binaries, or unrelated files.

## Android companion connection
The desktop remains the source of truth and exposes a local-only HTTP API for pairing, connection checks, and incoming capture transfer. The desktop server starts when Mobile App Setup is opened, remains active while the desktop runs, and shuts down with the application. The Android companion pairs by QR code or manual IPv4 address, stores its device token in Android secure storage, and retries connections while foregrounded. Desktop credentials are protected with Windows DPAPI in the portable configuration; moving that config to another Windows account or computer requires forgetting the saved pairing and pairing again. Authenticated transfer endpoints accept only bounded JSON metadata and JPEG multipart payloads; they expose no arbitrary filesystem or database operations.

HTTP traffic on the local network is unencrypted. Pair only on a trusted network. The app does not change Windows Firewall rules; users may need to allow BookLedger on Private networks.

Reconnection tries the last validated endpoint first, then Android NSD discovery of the desktop's DNS-SD advertisement, then the remaining saved IPv4 candidates. A successful discovered address becomes the new last-known endpoint. DNS-SD is supplementary; QR and manual address entry remain available when multicast is filtered. Windows hotspot discovery is implemented but has not been physically verified. Changed-IP recovery has unit coverage but has not been reproduced on the Poco.

## Incoming mobile captures
Each capture is identified by a UUID independently of its nullable ISBN. The Android client uploads metadata as a JSON multipart part and the original JPEG as a binary multipart part, with batch ID, expected count, and order. The JSON part is transient transport data: metadata is stored authoritatively in SQLite, not in individual JSON files or a batch manifest. `mobile_incoming_batches.batch_uuid` keys batch state and expected count. `mobile_incoming_captures.capture_uuid` keys each capture and references its batch through `batch_uuid`; the row stores sequence, nullable ISBN, capture time, and `photo_name`. That filename is the capture UUID plus `.jpg`, stored at `data/incoming/batch-<batch_uuid>/<capture_uuid>.jpg`. Desktop validates the request and JPEG, writes through a same-directory temporary file and atomic replacement, then commits the capture metadata before acknowledging it. Repeated capture UUIDs are idempotent; a batch becomes ready only when its expected captures are durably received. Incomplete reception remains staged and can be retried after restart.

Ready captures are processed in original sequence through the existing Add Book form. The incoming capture UUID is also the physical-copy UUID. The incoming row's link to that copy makes a crash after catalog save recoverable without creating a duplicate. After the catalog copy and canonical photo are verified, the staged JPEG and empty batch directories are removed; the SQLite row remains as an idempotency tombstone. Clear, Cancel, and Discard Incoming explicitly discard the current uncataloged capture and its staged file, while preserving other pending captures. Reception temporarily disables Add/Edit entry points while uploads are being written; it does not lock the rest of the desktop UI. No transfer or cataloged-incoming screen is added.

## Currency and SRP source review (November 2026)

BookLedger stores its application currency in SQLite `currency_state` and mirrors it to `config.json`. Schema v13 adds that state, the validated exchange-rate cache, and durable conversion audits; the v12 migration sets PHP without changing existing minor-unit amounts. Asking prices, all sale events (including voided history), and saved SRPs are converted together after a verified recovery backup. Amounts are calculated with `Decimal`, rounded half up to two minor digits, and committed in one SQLite transaction. The JSON conversion marker plus the database currency make startup reconciliation deterministic if the process stops between the database commit and config update. Frankfurter v2 rates are requested only for a user-approved conversion, cached with the observation and retrieval dates, and considered fresh for at most five days. If the live rate is older or unavailable, conversion stops without applying the stale value. Identical-currency operations do not request a rate. A fresh library and purge use PHP; a notation-only change preserves the numeric values. The supported ISO codes (PHP, USD, EUR, GBP, JPY, AUD, CAD, SGD, CNY, HKD, KRW, INR, TWD, THB, MYR, IDR, NZD, CHF, AED, SAR) were checked against the Frankfurter v2 currencies endpoint on November 20, 2026.
