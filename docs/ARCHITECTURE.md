# BookLedger Architecture (initial)

## Modules
- `bookledger.app`: main window, navigation, and page composition.
- `bookledger.ui.forms`: intake/edit form and field-level feedback.
- `bookledger.db.database`: SQLite connection setup, versioned schema migration, canonical locations, integrity checks, consistent snapshots.
- `bookledger.services.catalog`: validation, duplicate lookup, copy creation/editing, canonical location management, contextual price and explicit status/sales rules.
- `bookledger.services.isbn`: ISBN normalization, check-digit validation, and safe ISBN-10/ISBN-13 alias conversion (978 ISBN-13 only).
- `bookledger.services.metadata`: provider orchestration, field merging, and lookup outcomes. Open Library is primary, Google Books is the fallback/enrichment provider, and Booktopia is the final HTML enrichment source for supported missing fields.
- `bookledger.services.booktopia`: bounded HTTPS ISBN-search and product-page adapter. It verifies page ISBN evidence, parses matched schema.org Book data and standard description markup, and does not use Booktopia prices.
- `bookledger.services.photos`: image orientation, resizing, and JPEG compression.
- `bookledger.services.lifecycle`: durable trash, restore, clear, purge, and explicit recovery of file/database operations.
- `bookledger.services.verification`: read-only relational and managed-photo-tree consistency checks.
- `bookledger.services.backups`: verified backup archives and restore workflow.
- `bookledger.paths`: portable data locations and verified legacy-file migration.

## Data ownership
`book_records` owns bibliographic metadata shared by an edition/ISBN. `copies` owns physical-copy fields, the one current Price, and stable Copy IDs. `sales` is an append-only history of Price/date events; status reversals keep their recorded history and do not void revenue. A later transition back to Sold appends another event. Photo paths are stored relative to the portable data folder so moving the folder does not invalidate image references.

## Copy identity
Each copy receives an immutable UUID stored in `copies.copy_uuid`; this is its permanent identity across edits, status changes, backups, and restores. The existing integer `copies.id` remains a local row handle for current SQLite foreign keys and GUI callbacks. `copy_code` remains the human-facing `BL-` identifier, formatted from that local ID and displayed in reports and messages. UUIDs are not derived from either value. Schema v7 adds the UUID to existing copies without changing their row IDs or visible codes. The app does not yet merge independent libraries; UUIDs alone do not identify duplicate physical books.

## UI/business boundary
UI callbacks gather input and display service results. Core validation and persistence rules are enforced in `CatalogService` and SQLite constraints. Long-running metadata lookup runs off the UI event thread, with provider activity, provider outcomes, and the overall result passed back through a UI queue and applied on Tk's thread. Each provider outcome distinguishes a confirmed miss, an unverified returned record, a matched record with sparse metadata, a recognized unavailable product, and categorized lookup failures; user-visible diagnostics avoid raw exception details. Partial results without a description are reported as such, including when Book Details is unavailable. Operation IDs and the requested ISBN guard against stale callbacks after an ISBN change, form clear, or newer lookup. The application configures Open Library, Google Books, then Booktopia. Open Library queries the exact ISBN and its valid ISBN-10/13 alias together, but does not provide Book Details/Synopsis from edition descriptions, notes, excerpts, or linked-work descriptions. Google Books tries the exact raw ISBN, the exact `isbn:` query, then the equivalent `isbn:` query when needed; it scans all returned volumes and combines non-empty fields only from candidates whose ISBN matches either valid representation. Sparse matching results do not prevent later candidates or query variants from supplying a description. Google identifiers must match either valid representation, while Open Library accepts a response keyed to the requested ISBN if identifiers are absent and rejects conflicting identifiers. Booktopia queries `search.ep?keywords={isbn}`, follows at most two HTTPS links on Booktopia whose product URL carries the requested ISBN or valid alias, and requires a matching ISBN on the product page. If the search request returns an HTTP error without a verified product, it makes one request to `https://booktopia.com.au/book/{isbn}.html/`; the normal redirect handler permits only same-site HTTPS redirects. Data from that fallback is accepted only when the final URL is a slugged canonical product URL and the page independently verifies the requested ISBN. It reads title, author, publisher, publication year, edition, page count, and recognized print format from the matching schema.org Book object. For Book Details, it uses the Description panel only when the `#pdp-tab-description` tab explicitly identifies that panel through `aria-controls`, an in-page `href`/target relationship, or the panel's `aria-labelledby`. If there is no linked panel, a matching schema.org Book description is considered after rejecting recognized bibliographic-note and retail boilerplate text. Generic page metadata and unassociated `itemprop="description"` content are not used. If no usable synopsis remains, Book Details stays empty. An explicit page message that the book cannot be sourced, or a matching structured `OutOfStock`, `Discontinued`, or `SoldOut` value, sets the provider outcome to `Product unavailable` without treating the matched ISBN as missing. A Booktopia HTTP error body may still be used if its final URL is the canonical URL for the requested ISBN, page ISBN evidence matches, and supported metadata is present; otherwise the original HTTP/provider failure is retained. Booktopia does not map product price to Price or SRP. Booktopia pages with no ISBN evidence are reported as unverified; unexpected parsing errors remain provider failures rather than ISBN misses. Google Books `volumeInfo.description` is supported. Provider-derived titles are normalized, and values are merged into empty controls only, preserving both earlier provider values and user input. The Add Book form includes a photo preview and simulated BookLedger Mobile connection and ISBN scanning controls. Metadata providers can be replaced without changing the catalog schema or form workflow.

Booktopia uses standard-library HTML parsing only; there is no browser automation or additional dependency. It caps each response at 2 MiB, applies the provider's ten-second timeout to each request, and restricts redirects/product links to HTTPS Booktopia hosts. The same size and host checks apply to HTTP error bodies. A search response may lead to at most two ISBN-10/ISBN-13 candidate requests; when the search request returns an HTTP error, one direct ISBN URL is attempted instead. A search response without a verifiable product link is reported as ISBN unconfirmed, not a confirmed miss. Provider skipping checks each provider's supported fields, including Book Details/Synopsis for Google Books and Booktopia; only missing values are merged. The form supports print format but has no language or series field; those attributes are not stored. Booktopia's current Terms of Business state that bibliographic data is copyrighted by Nielsen Book Services, publishers, or their licensors, but do not establish an automated metadata API or permission. This HTML integration is best-effort and subject to Booktopia's policies and page changes. Current live raw HTML and the Description-tab relationship were not available for inspection; synthetic fixture tests verify the relationship-aware parser but do not establish current live-site behavior.

Catalog and Inventory share `CatalogService.list_copies()` and the same active physical-copy rows; trashed and pending storage-operation rows are filtered centrally. Catalog presents one photo card per copy, including stable Copy ID, Price, and a gray overlay/red SOLD marker; double-click opens read-only More Details. Inventory presents a sortable detailed table; double-click edits the clicked row. Both expose the same right-click context menu; Delete moves exactly one copy to Trash. Dashboard counts and ordinary sales/revenue exclude copies in Trash. Restore preserves the row and its sales events; Clear Trash permanently removes those sales events and conditionally removes an unreferenced bibliographic record.

Schema v4 includes `trash_entries` and `storage_operations`. Trash metadata references the original copy row and records its previous status and deletion order. Storage operations make interrupted photo install/replace/trash/restore/cleanup detectable and expose explicit retry. Database transactions and file moves are coordinated by services; a filesystem operation is not considered complete while its durable journal remains.

## Portable storage and migration
`AppPaths` resolves the project root during source development and the executable directory when frozen. Writable application data is under `data/`: `bookledger.sqlite3`, `photos/{copy_id}.jpg`, `trash/{copy_id}.jpg`, and non-configuration assets. Root-level `config.json` owns application settings; root-level `backups/` and `log.txt` are preserved by Purge. Startup detects legacy `BookLedger_Data/` before database initialization, snapshots SQLite through its backup API, copies photos/assets/backups, checks the copied database, canonicalizes referenced old photos to per-ID JPEGs, and only then renames the legacy folder to a `.migrated` recovery folder. Both-database conflicts stop startup. Configuration updates use an atomic replacement and preserve unrelated JSON keys. If the root configuration cannot be read or written, the existing profile configuration may be used as a safe fallback; malformed source files are preserved.

New and replacement images are processed through `PhotoService` into `photos/.staging/` and become canonical only once fully decoded and compressed. New copies reserve their generated ID in SQLite and journal the canonical installation; replacements use same-volume atomic replacement so the old image remains until the staged replacement is ready. Mobile photo handoff and Choose Photo both call the same staging service.

## Trash and verification
Delete journals then moves one canonical photo to `trash/{copy_id}.jpg` and inserts a `trash_entries` row without deleting the copy or its sales history. Restore selects the latest Trash entry (LIFO), moves the original photo back, and removes Trash metadata only after the file move. Clear Trash deletes selected sales/copy/trash rows in a transaction, removes bibliographic records only when no copies remain, then removes unshared files; a cleanup failure remains in `storage_operations` for explicit retry. Purge requires two UI confirmations including the exact word `PURGE`, clears only resolved children within `data/`, and retains root backups.

`VerificationService` does not mutate data. It checks SQLite integrity and foreign keys, copy identities, Trash consistency, unresolved storage operations, canonical and safe photo paths, missing active/trashed photos, unreferenced files, shared paths, and staging residue. Warnings do not trigger cleanup.

`config.json` is the canonical configuration document. It retains the existing `metadata_providers` section and holds `api_keys.google_books`, `preferences.genres`, `preferences.formats`, `preferences.locations`, and `logging.enabled`; `migration_state` records one-time legacy migration checks. The Google Books key is stored as plain text and is never written to `log.txt`. Backup archives are not encrypted and include the canonical configuration, so they may contain API credentials. A canonical key takes precedence over any older key; when absent, the portable `data/assets/google_books.json` value takes precedence over a profile legacy file. The portable legacy file is removed only after the root configuration has been written and read back successfully with the migration marker and when it contains no unrelated settings. Conflicting, malformed, or extra-field legacy files are preserved and are not active sources after the migration is checked. A profile legacy file is retained as recovery data but is inactive after the marker is written. Removing the canonical key does not re-import either legacy value.

Genre, Format, and Location options migrate once from SQLite configuration (`app_meta` and `locations`). Assigned historical values absent from those lists are retained as compatibility options. After migration, these option lists are read and written through `config.json`; SQLite continues to own book and copy assignments, sales, and all other operational records. Legacy `app_meta` and `locations` entries remain in the database as inactive migration data and are not synchronized with the canonical lists. `logging.enabled` migrates from `app_meta.diagnostic_logging_enabled`; the legacy value is no longer updated after migration. `log.txt` contains optional diagnostic events only.

## Snapshot backup and restore
Backups are versioned ZIP snapshots with a manifest of file sizes and SHA-256 checksums. They contain a consistent SQLite snapshot, managed `data/photos/`, `data/trash/`, `data/assets/`, and root `config.json`. The diagnostic log, caches, application binaries, and files outside those managed components are excluded. Backup names include a local timestamp and random suffix; an archive is published only after it validates. If a backup destination is inside managed data, that destination subtree is excluded from the snapshot.

Restore replaces the current database, photos, trash, assets, and root configuration with the selected snapshot; it never merges later edits. The UI warns about the replacement and asks for confirmation. Before activation, BookLedger creates and retains a separate validated snapshot of the current library in `backups/`. The selected archive is checked for safe paths, supported manifest, checksums, valid configuration, SQLite integrity, foreign-key integrity, and referenced photos. Components are staged and activated under a durable recovery journal. If activation fails or the process stops mid-swap, the next startup restores the prior component set before opening the library. Successful restore keeps the pre-restore recovery archive. Restart BookLedger after restore so in-memory provider/configuration settings reload. Archives are not encrypted and may contain API credentials from `config.json`; store them accordingly. Restore does not promise to retain excluded logs, caches, binaries, or unrelated files.

## Future Android interface
The desktop remains the source of truth. A future local service should expose only explicit pairing, ISBN submission, photo upload, acknowledgement, and session/capture identifiers. The phone must never open or mutate the SQLite file directly. This local service is intentionally not part of the current build; the current intake controls only simulate connection and scan events.
